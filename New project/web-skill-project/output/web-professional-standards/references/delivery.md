# Stack, delivery and maintenance

Choose the smallest deployable architecture the team can operate. Identify the content editor, publication frequency, dynamic requirements, hosting features, budget and who will respond to failures. Keep an existing stack when it meets these constraints.

- Static output suits infrequently edited public content with a build and release owner. A CMS can justify its cost when editors need drafts, roles, localization or media workflows. Check backups, update responsibility and export. Server-rendered or interactive code needs a compatible runtime, persistent data strategy and accessible fallback for its critical path. Verify which features survive a platform’s static export.
- For BiH or diaspora audiences, confirm language variants, diacritics, place and contact formats, time zone, currency and business claims with the client. Check who receives data and where. For questions of jurisdiction or legal basis, give the responsible person the actual data flow and the applicable official source. Record their decision for this project.
- Before release, verify real hosting behavior for HTTPS, canonical host, redirects, routing, headers, cache and secrets. Establish who controls DNS, renewal, mail and service accounts. A form provider accepting a request cannot establish mailbox delivery. Give critical external dependencies an observer and recovery contact.
- Version important assets. For changes to a data contract, allow old and new readers to coexist. Rehearse migration and restore in an approved comparable environment, define the stop signal, recovery steps and owner. Reverting application code alone may leave incompatible writes.
- Hand over access through approved channels, editing instructions, deployment and rollback steps, recovery responsibilities and the smallest regression set for common updates. Agree actionable monitoring, redacted logs, supported dependency versions and who can disable a failing integration.
