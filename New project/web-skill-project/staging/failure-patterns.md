# Known failure mechanisms · authoring copy

Consult only after recording project-derived findings. Severity is conditional on the actual consequence. The controls below are inferred engineering choices. The evidence notes distinguish specification behavior from the proposed remedy.

## Interface and public content

- **UI-INTRINSIC.** Long localized text or media enters a narrower component. A track or child keeps its intrinsic minimum and the action moves offscreen (R0 if it becomes unreachable). Allow the responsible item to shrink or wrap. Keep necessary two-dimensional material in an operable local region. Check long and ordinary content at the failing width.
- **UI-ORDER.** A layout pairs captions, prices or choices by visual placement. Reflow or a missing item changes which label appears to belong to which object (R1, potentially R0 for a wrong transaction). Bind each label to its object in the content and reading order. An intentionally separate key can work if associations remain explicit. Inspect linearized and narrow layouts.
- **UI-FOCUS.** A responsive disclosure or sticky layer changes what is visible while keyboard focus continues elsewhere (R0 on the only route to the task). Define open, close and focus behavior for the chosen interaction. A simple disclosure need not trap focus. Use only a keyboard, expand, follow a link or dismiss, and locate focus at increased text size.
- **UI-MOTION.** Essential content or state is revealed only after an animation, observer or hover event (R0 when there is no usable alternative). Render the end state accessibly first. Add the cue where it helps orientation. Decorative-only effects can disappear. Complete the task with reduced motion, touch and the enhancement unavailable.
- **UI-MEDIA.** A prominent image or font arrives late, displaces the action or hides key detail in a new crop (R1, or R0 when it changes a selection). Reserve space, retain legible fallback and expose the critical resource early. Below-fold imagery can still be deferred. Inspect the actual crop and action during loading on relevant layouts.
- **UI-CLAIM.** A draft contact, stock portrait, accreditation or review is presented as authentic (severity follows harm, R0 for a critical false claim). Record the source or remove the claim from the release scope. A clearly labeled concept can stay in a preview. Match the rendered material to approved facts, permissions and required credits.
- **UI-ROUTE.** A shared title, shell or HTTP success response makes an error route look like the intended page (R1; higher if an essential route is lost). Give tests an independent page identity and verify the destination content. A deliberate fallback has its own expected status. Check an expected route, a moved URL and an unknown one.

Evidence trail: B1 and [sizing/reflow](../research/notes-1B.md), C1 and [identity, user tasks and rights](../research/notes-1C.md), E1–E3 and [proof limits](../research/notes-1E.md). UI-ROUTE combines route identity with the limits of a status code. No pattern has been evaluated on an independent brief.

## Services, data and ownership

- **SV-REPLAY.** A durable operation can finish before the client receives its reply. Retrying under a new identity can apply it twice (R0 for payment or scarce stock). Resolve the existing outcome or reuse a supported operation identity with the same intent. A read-only request has different semantics. In a sandbox, compare the authoritative record and user message after the retry.
- **SV-CONTENTION.** Different valid requests depend on the same prior availability or revision. Both can pass a client precheck (R0 for a conflicting commitment). Put the business condition at the write boundary, handle loss of the race and refresh the losing view. Independent resources need no shared lock. Observe both outcomes and the final state.
- **SV-SIGNAL.** A late, repeated or missing provider event drives a terminal state or the UI declares delivery on acceptance (R0/R1 by consequence). Authenticate provider events as required, reconcile state by identity and advance only on the contracted evidence. Simple receipt-only forms can say ‘received’. Check provider, business record and final delivery separately.
- **SV-AUDIENCE.** An authenticated identity is treated as entitled to every matching object, or a private response is reused by a shared cache (potential R0 exposure). Enforce resource authorization and limit reuse to the correct audience at each serving layer. Public material may be cacheable. Review rules and compare authorized test identities on isolated records.
- **SV-INPUT.** Editor content, uploads or form values cross into a new output or storage context (R0/R1 by reachable impact). Validate the business shape and permissions on the server; use context-safe rendering, parameterized database access and bounded file handling where present. Plain text needs less machinery than rich HTML. Inspect each actual consumer and approved sample.
- **SV-RELEASE.** Old readers or open tabs continue using a previous asset or data contract after deployment (R1/R0 if records are lost). Keep overlapping versions compatible through cutover and define when old assets or columns may retire. A disposable preview has a simpler recovery path. Check old/new reads, new writes and the recovery plan.
- **SV-OWNER.** A managed form, DNS record, map, language feed or domain can outlive the account that maintains it (R1/R0 on a sole contact channel). Name an owner, observable failure and workable fallback. A decorative embed need not acquire a heavy monitor. Follow a synthetic request to its authorized destination and verify who can recover the service.

Evidence trail: D1/D2 and [server-side decisions](../research/notes-1D.md), F1/F2 and [release, caching, mail and ownership](../research/notes-1F.md). Provider-specific behavior must be checked against the actual service contract and version. QA authority ends at the layer it can observe.
